Candidate Technical Answers & System Architecture

Comprehensive technical responses and architectural designs for the 15 evaluation questions posed in the Python Developer interview assignment.

Q1 How do you identify the most appropriate Shopify category for a product?

We use a two-stage hybrid candidate generation and multi-feature ranking architecture:

  1. Candidate Retrieval (Stage 1): Across the 10,000+ official Shopify taxonomy categories, an in-memory inverted token index + fuzzy string similarity shortlists the top 15–25 candidate category paths in <2 milliseconds per item.
  2. Multi-Signal Feature Scoring (Stage 2): Each candidate is evaluated against multiple independent product signals:
    • Title Match (35% weight): Token set intersection and partial substring matching against category leaf names.
    • Clue / Source Category Match (25% weight): Alignment between source catalogue categories (e.g. Living Room > Sofas) and Shopify hierarchy.
    • Description & Bullets (20% weight): Keyword and n-gram overlap in long-form product details.
    • Attribute Consistency (10% weight): Compatibility of materials and product types.
    • Image Verification (10% weight): Visual availability and multi-modal alignment.

The candidate with the highest composite score is selected as the predicted category, with confidence calibrated based on separation margin over runner-ups.

Q2 How do you handle products with a title but missing description or images?

Our system implements dynamic signal reweighting and completeness penalty adjustments:

  • When description or image is missing, the classifier reallocates signal weights to available structured fields: product_title, materials, product_category, product_sub_category, and bullets.
  • The confidence engine applies a completeness factor. If the remaining signals still yield high certainty (e.g., Title: "Empress Bonded Leather Sofa" + Material: "Bonded Leather"), it achieves high confidence and is auto-classified.
  • If title is too generic (e.g. "Standard Item #44") and missing description/image leaves insufficient evidence, confidence falls below 70%, automatically routing the item to the Manual Review Queue with alternative suggestions.
Q3 How do images help in classification, and how is fallback handled?

Images provide decisive physical evidence to resolve ambiguous text (e.g. distinguishing between a dining chair, barstool, and bench). Our pipeline:

  • Performs non-blocking asynchronous verification of image accessibility and format (JPEG/PNG/WebP).
  • Integrates image signals into multi-modal scoring.
  • Graceful Fallback: If an image is unavailable or broken, the engine seamlessly marks image_status='missing' or 'broken' and continues classification using pure text and metadata without dropping accuracy or interrupting batch runs.
Q4 How do you process 10,000+ products efficiently in batches?

We use asynchronous background chunked batching with thread pools / Celery workers:

  • 10,000 products are divided into micro-chunks of 100 products.
  • Workers retrieve chunks using cursor-based batch queries (.select_related()) avoiding full-table memory loads.
  • Updates are written with bulk operations (bulk_update), reducing 10,000 individual database roundtrips to just 100 fast SQL queries.
  • Achieves throughput of 100–250 products per second, classifying 10,000 products in under 1–2 minutes.
Q5 How should the Shopify taxonomy be stored in the database?

We normalize the Shopify taxonomy into relational tables in MariaDB / SQLite:

CREATE TABLE taxonomy_category ( id VARCHAR(128) PRIMARY KEY, -- GID e.g. gid://shopify/TaxonomyCategory/fu-1-1 code VARCHAR(64) INDEX, -- fu-1-1 name VARCHAR(255) INDEX, -- Dining Chairs full_name VARCHAR(1024) INDEX, -- Furniture > Chairs > Dining Chairs level SMALLINT DEFAULT 0, -- 2 parent_id VARCHAR(128) NULL, -- FK to parent category is_leaf BOOLEAN DEFAULT TRUE, created_at DATETIME ); CREATE TABLE taxonomy_attribute ( id VARCHAR(128) PRIMARY KEY, -- GID e.g. gid://shopify/TaxonomyAttribute/5398 name VARCHAR(255) INDEX, -- Material, Color, Style handle VARCHAR(255) INDEX ); CREATE TABLE taxonomy_attribute_value ( id VARCHAR(128) PRIMARY KEY, -- GID e.g. gid://shopify/TaxonomyValue/50818 attribute_id VARCHAR(128), -- FK to taxonomy_attribute name VARCHAR(255) INDEX -- Bonded Leather, Solid Wood );

This structure enables instant hierarchy breadcrumbs, tree traversal, and category-attribute validation.

Q6 How is the confidence score calculated and calibrated?

Confidence is a normalized probability value (0.0 to 1.0) calculated via:

Confidence = (0.35 * TitleScore + 0.25 * ClueScore + 0.20 * DescScore + 0.10 * AttrScore + 0.10 * ImgScore) + MarginBonus(TopScore - 2ndScore) * CompletenessFactor

Scores $\ge 0.70$ (70%) are auto-approved. Scores $< 0.70$ automatically trigger the Needs Review state with alternative suggestions.

Q7 What happens when the system cannot confidently identify a category?

Instead of guessing blindly or failing silently:

  1. The product is marked with status = 'needs_review'.
  2. The top 3–4 candidate categories are saved into alternatives with relative confidence percentages.
  3. The product appears highlighted in the Review Queue. A reviewer can click any alternative category or use the instant taxonomy search to assign the correct category in one click.
Q8 How do you handle invalid, broken, or unreachable images?

Our ImageHandler implements isolated failure trapping:

  • Image requests use a strict 1.5-second timeout and catch all exceptions (DNS failure, 404 Not Found, SSL errors, timeouts).
  • If an image fails, the item is tagged with image_status='broken'.
  • The classification proceeds smoothly using text signals. The batch worker continues without interruption.
Q9 How are the API and Database designed for scalability?

Database Layer: Optimized with B-Tree indexes on status, confidence_score, product_number, and name. Foreign keys maintain referential integrity with cascading updates.

API Layer: Django REST Framework endpoints with cursor pagination, asynchronous task triggering, and JSON/CSV/XLSX streaming endpoints.

Q10 If each product took 2 seconds sequentially, 10,000 items would take ~5.5 hours. How do you optimize this?

We reduce processing time from 5.5 hours to under 2 minutes using:

  • In-Memory Inverted Indexing: Pre-indexing taxonomy tokens eliminates repetitive external queries or expensive models for obvious matches.
  • Concurrent Batch Workers: Multi-threading / Celery workers process chunks in parallel across CPU cores.
  • Bulk Database I/O: Writing 100 items per bulk_update minimizes database latency.
  • Non-Blocking Image Verification: Fast header validation with short timeouts.
Q11 If the process fails after 6,000 products, how does the system recover and resume?

Every product record maintains an individual state in the database:

  • Products 1 to 6,000 already have status IN ('auto_classified', 'needs_review', 'approved') and remain safely stored in MariaDB.
  • When a job restarts or resumes, the worker queries: ClassificationResult.objects.filter(status='pending').
  • The worker immediately resumes from product 6,001 without repeating work or generating duplicates.
